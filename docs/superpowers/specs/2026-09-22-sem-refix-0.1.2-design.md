# StatLab SEM Re-fix (post-`@statlab/core@0.1.2`) — Design

**Date:** 2026-09-22
**Status:** Approved
**Phase:** Follow-up to Phases A and B of the "bring `@statlab/core`'s `sem.js`
module to the webapp" initiative. Phase A (merged) added `pathAnalysis` but
reverted `sem` after manual verification found its factor-loading Newton-
Raphson optimizer (`_fitRAMByML`) silently stalls at the parameters' initial
guess — confirmed across every tested dataset, including a synthetic one
deliberately built with an ideal, unambiguous factor structure. Phase B
(merged) added `latentGrowthModel` and `bifactorModel`, the two functions
confirmed structurally independent of that optimizer, and shipped
`bifactor` with its `omegaTotal`/per-item `communality` hidden (a separate
bug: the package's `group` loading was never capped, and — as the
upstream fix later revealed — the whole factor extraction ran on a raw
covariance matrix instead of a correlation matrix). Upstream bug reports
for both were filed as follow-ups; both have now been fixed, verified,
and published as `@statlab/core@0.1.2`.

## Problem

`@statlab/core@0.1.2` is out. Reading its changelog/PR history and
independently re-running the exact repro cases that originally found each
bug (not just trusting the fix descriptions) confirms:

- **`sem()`'s loading optimizer is genuinely fixed.** Root cause: the
  Newton step `-H⁻¹∇f` is only a descent direction when the numerically-
  estimated Hessian is positive-definite; at the loading parameters'
  initial guess it isn't, so the step pointed uphill, the line search
  exhausted all halvings without finding improvement, and every
  subsequent iteration repeated identically. Fixed by falling back to
  steepest descent when the Newton step isn't a genuine descent
  direction. Re-verified against the original ideal-dataset repro
  (n=300, true loadings 0.7–0.85): loadings now recover to within ~0.07
  of ground truth with sane, non-zero, non-infinite SEs (~0.14–0.15),
  and fit indices are internally consistent (χ²(2)=3.66, p=.16, CFI=.999,
  RMSEA=.053 — no more CFI/RMSEA contradiction).
- **`bifactorModel()`'s `omegaTotal`/`communality` are genuinely fixed** —
  and the real root cause was deeper than the filed report guessed:
  factor extraction ran on a raw covariance matrix rather than a
  correlation matrix (unlike `pca`/`efa` elsewhere in the same package),
  so capping the `group` loading alone wouldn't have been sufficient.
  Fixed by standardizing to a correlation matrix before extraction,
  capping `general`+`group` jointly, and correcting the `omegaHierarchical`/
  `omegaTotal` formulas against the verified Rodriguez, Reise & Haviland
  (2016) reference (the old `omegaTotal` formula wasn't computing omega-
  total at all — it was mean per-item communality). Re-verified against
  both original repro cases: mixed-scale (`omegaTotal`: 11902.38 → 0.886)
  and same-scale (`communality`: 16.33 → ≤0.99), both now correctly
  bounded.
- **`ordinalSEM()` turns out to also be fixed, as an unplanned bonus.**
  It reuses `_fitRAMByML` directly (confirmed by reading its source: "the
  same RAM-ML machinery as `sem()`"), so it inherited the same fix. Not
  previously identified as independently viable — the original Phase B
  scoping lumped it in with `semMultiGroup`/`measurementInvariance` under
  a shared "deferred, same broken optimizer" assumption, which turns out
  to have been imprecise: `ordinalSEM` shares `_fitRAMByML` with `sem`;
  `semMultiGroup`/`measurementInvariance` share the separate
  `_fitMultiGroupCFA`, confirmed *not* part of this fix (re-verified: a
  fresh `measurementInvariance` run still shows the exact broken
  signature — `deltaChi2 = 0, p = 1.000` for both the Metric and Scalar
  steps, meaning the constrained and unconstrained models produce
  identical fit because neither ever moved past its shared initial
  guess). Verified `ordinalSEM` independently on a fresh synthetic
  dataset: real, distinct loading estimates (0.98, 0.97) with finite,
  plausible SEs (0.53), not the stuck-at-initial-value pattern.

## Goals

1. Re-add `sem` to the SEM Navigator category exactly as Phase A designed
   it (same equations-textarea config, same `SemCoeffTable`/fit-index
   rendering, same `semResultOrError` convergence guard — kept as
   defense-in-depth; a fixed optimizer can still fail to converge on a
   genuinely mis-specified model, and the guard costs nothing to keep).
2. Un-hide `bifactor`'s `ωt` chip and `communality` table column, restore
   the un-truncated `apa` string, remove the `r.warning` banner and the
   method-note caveat added as the Phase B workaround.
3. Add `ordinalSEM` to the SEM category: reuses the existing
   `scaleVars`/`CheckList` control (3+ ordinal/Likert items) plus one new
   `Inp` for the factor name/label (default `'f1'`, matching the
   package's own default parameter). Results reuse `SemCoeffTable`
   (relabeling `indicator`/`factor` fields to fit its existing
   `from`/`estimate`/`se`/`z`/`p` column shape) plus a fit-index `Chip`
   row modeled on `sem`'s own (χ², df, p, CFI, TLI, RMSEA only — this
   function's `fit` object has no SRMR/AIC/BIC).
4. No new build/runtime dependency beyond the `@statlab/core` version
   bump itself (`^0.1.1` → `^0.1.2`).

## Non-goals

- `semMultiGroup`/`measurementInvariance` — confirmed still broken
  (`_fitMultiGroupCFA` unfixed), remain deferred. A follow-up bug report
  for that optimizer was already filed during the `sem()` fix work.
- `ordinalSEM`'s `nThresh` option — not exposed, matching the established
  "don't expose algorithm internals" precedent (`sem`'s own
  `maxIter`/`tolerance`, `bifactorModel`'s `maxIter`).
- The raw polychoric correlation matrix (`r.R`) and per-item threshold
  cutpoints (`r.thresholds`) `ordinalSEM` also returns — not rendered.
  Diagnostic detail not essential for a first pass; every other test in
  this app similarly surfaces the headline coefficients/fit, not every
  intermediate computation.
- `cfiCompare` (Phase C) — still blocked. It compares two SEM-model fit
  objects; with `sem`/`ordinalSEM` now reliable, Phase C is no longer
  blocked on *availability* of a fit-producing function, but its own
  brainstorming (the 2-model comparison UI, with no precedent anywhere
  in this app) was never started and stays its own follow-up, not
  folded into this one.

## Approach

### Changes to existing code

**`sem` re-add:** revert Phase A's revert commit's changes verbatim —
`tree.js` (TREE entry), `runners.js` (runner + import), `chartMap.js`/
`chartMap.test.js` (entry + count bump), `contracts.test.js` (count
bump), `InferenceConfig.jsx` (config entry), `InferencePanel.jsx`
(`semEquations` state, `useMemo` deps entry, `useInference` return
entry, `semResultOrError` helper, computation branch, import),
`InferenceResults.jsx` (`SemCoeffTable` component, result block),
`methodNotes.js` (entry), `InferencePanel.test.jsx` (the 2 non-
convergence regression tests). Exact code already exists in git history
(the revert commit's parent) — this is a mechanical re-application, not
a redesign, though every anchor must be re-verified against the current
file state before insertion (Phase B's own commits touched several of
the same files in between).

**`bifactor` un-hide:** revert the Phase B Task 3 workaround commit's
changes to `InferenceResults.jsx` (`BifactorTable`'s `communality`
column, the `ωt` chip), `InferencePanel.jsx` (the `apa`-rebuild and
`warning` wrapper around the `bifactor` branch — remove entirely, call
`bifactorModel` directly again), and `methodNotes.js` (drop the
caveat sentence from `bifactor`'s `assumptions` array). The dataset-
switch revalidation fix for `bifactorGroups` (a genuinely separate,
still-valid bug fix, unrelated to the omega bug) stays untouched.

### New: `ordinalSEM`

| TREE id | Label | Category | Call |
|---|---|---|---|
| `ordinal_sem` | Ordinal SEM | SEM | `ordinalSEM(data, vars, ordinalFactorName.trim() || 'f1')` where `vars = scaleVars.filter(c => numeric.includes(c))` |

`ordinalSEM` internally requires `data.length >= 20`, `vars.length >= 3`,
and a truthy `model` string (the webapp always supplies a non-empty
string via the `|| 'f1'` fallback, so this can never trip). Reuses
`scaleVars`/`setScaleVars` (already shared by `pca`/`sem`'s siblings —
no new variable-selection state). One new dedicated state,
`ordinalFactorName` (string, default `'f1'`), rendered via:

```js
ordinal_sem: <>
  <CheckList label="Ordinal / Likert items (3+)" items={numeric} selected={scaleVars} onChange={setScaleVars} />
  <Inp label="Factor name" value={state.ordinalFactorName} onChange={state.setOrdinalFactorName} width={100} placeholder="f1" />
</>,
```

Result rendering reuses `SemCoeffTable` (already built for `sem`,
Phase A) on `r.loadings.map(l => ({ from: l.indicator, estimate: l.estimate, se: l.se, z: l.z, p: l.p }))` —
a thin field-rename mapping, not a new table component:

```js
{r.test === 'Ordinal SEM' && <>
  <SectionHead label={`Ordinal SEM · n=${r.n}`} />
  <Row>
    <Chip label="χ²" value={r.fit?.chisq} sub={`df=${r.fit?.df}`} color={C.dim} />
    <Chip label="p" value={r.fit?.p != null ? fmtP(r.fit.p) : '—'} color={sig(r.fit?.p) ? C.neg : C.ok} />
    <Chip label="CFI" value={r.fit?.cfi} color={r.fit?.cfi >= .95 ? C.ok : r.fit?.cfi >= .90 ? C.warn : C.neg} />
    <Chip label="TLI" value={r.fit?.tli} color={C.dim} />
    <Chip label="RMSEA" value={r.fit?.rmsea} color={r.fit?.rmsea <= .06 ? C.ok : r.fit?.rmsea <= .08 ? C.warn : C.neg} />
  </Row>
  <SemCoeffTable coeffs={(r.loadings ?? []).map(l => ({ from: l.indicator, estimate: l.estimate, se: l.se, z: l.z, p: l.p }))} />
</>}
```

(`ordinalSEM`'s own `fit` field is named `chisq`, not `chi2` like
`sem`'s — read directly from the source rather than assumed, since this
exact naming mismatch was the thing `cfiCompare`'s own Phase A design
note flagged as a real inconsistency between the two functions.)

### Error handling

`ordinalSEM` has its own documented non-convergence path distinct from
`sem`'s: reading the source, when `_fitRAMByML` fails outright it
returns a result with `fit: { chisq: NaN, rmsea: NaN, cfi: NaN }` and
`loadings: []` rather than returning `null` — the function's own comment
calls this "model did not converge". The existing "Configure parameters
to the left." fallback (triggered only by a `null`/falsy result) does
NOT cover this case, so a dedicated guard is needed, following the same
`{ error }` convention as `sem`'s:

```js
if (a === 'ordinal_sem') {
  const vars = scaleVars.filter(c => numeric.includes(c));
  const r = ordinalSEM(data, vars, ordinalFactorName.trim() || 'f1');
  if (!r) return null;
  return Number.isFinite(r.fit?.chisq) ? r : { error: 'Ordinal SEM model did not converge — try fewer items or a simpler factor structure.' };
}
```

### Contract test fixtures

`ROWS` (`mkTabular()`) has `item1`-`item4` (small-integer-valued,
already used by `pca`/`efa`/the MDS tests) — suitable as ordinal/Likert-
style items without a new fixture. `sem`'s runner is restored verbatim
from the revert's parent commit (`f1 =~ item1 + item2 + item3`, already
independently confirmed to converge in Phase A).

## Testing

- `src/config/contracts.test.js` covers `sem` (restored) and
  `ordinal_sem` (new) automatically once their runners exist; current
  `main` (post-Phase-B) has `TREE_IDS.length` at 231 — this plan adds 2
  new ids (`sem` restored, `ordinal_sem` new; `bifactor`'s un-hide adds
  no new TREE id), so the literal bumps 231 → 233.
- `chartMap.test.js`'s hardcoded mapping-count literal is currently 233
  (post-Phase-B); bumps to 235 for the same 2 new entries, including its
  own title string.
- Restore the 2 `InferencePanel.test.jsx` regression tests for `sem`'s
  non-convergence guard exactly as Phase A wrote them (the fixtures
  that broke `sem` before the fix should — and must be re-verified to —
  no longer break it after 0.1.2; if either fixture now converges
  cleanly instead of hitting the guard, that test needs a different,
  still-genuinely-degenerate fixture, found the same way Phase A found
  the original ones: empirically, against the real package).
- A new regression test for `ordinal_sem`'s non-convergence guard,
  found empirically against the real 0.1.2 package (not assumed) —
  a dataset/config combination that genuinely trips `ordinalSEM`'s own
  `fit.chisq: NaN` path, the same rigor every prior guard test in this
  app has used.
- Manual pass in the Browser preview: run `sem` and confirm it computes
  a real, sane result on the dataset-derived default equation (not just
  that it renders without throwing); run `bifactor` and confirm `ωt`/
  `communality` are visible again and land in `[0,1]`; run `ordinal_sem`
  against a bundled dataset's numeric columns and confirm it computes.
