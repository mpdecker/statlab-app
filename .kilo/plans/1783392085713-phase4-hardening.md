# Phase 4: Hardening — Edge-Case & Guard Tests for All 90 Modules

## Context

Phases 1-3 completed oracle test coverage for all 84 method modules + 6 math modules (90 total). The hardening.test.js file covers only 11 of 90 modules with ~32 edge-case tests. This phase adds hardening `describe()` blocks to every module's `.test.js` file.

**Decisions:**
- Per-module test files (add `describe('hardening — ...')` blocks to each existing `.test.js`)
- All 90 modules in one phase (including filling gaps in the 11 partially-covered modules)
- No changes to `gen-reference.py` — hardening tests use local test data, not oracle fixtures

## Hardening Categories

Each module gets 1-3 describe blocks covering applicable categories:

### G — Null/Invalid Input Guards (all modules)
Test that every exported function returns `null` or handles gracefully for: empty arrays, zero-length inputs, negative dimensions, out-of-range parameters, mismatched array lengths, missing required fields.

**Template:**
```js
describe('hardening — invalid inputs', () => {
  it('functionName returns null for bad input', () => {
    expect(functionName([])).toBeNull();
    expect(functionName(null)).toBeNull();
  });
});
```

### D — Degenerate/Boundary Data (data-computing modules)
Test behavior on: constant vectors, all-same-class data, zero-variance, single-element groups, collinear predictors, very small samples (n=1, n=2).

**Template:**
```js
describe('hardening — degenerate data', () => {
  it('handles constant data', () => {
    expect(functionName([5,5,5,5], ...)).not.toBeNull();
  });
});
```

### R — Reproducibility (stochastic/PRNG modules)
Verify `same seed + same input → identical output`. Applies to modules using `mulberry32` or other seeded RNG.

**Template:**
```js
describe('hardening — reproducibility', () => {
  it('same seed yields same result', () => {
    const a = stochasticFn(data, { seed: 42 });
    const b = stochasticFn(data, { seed: 42 });
    expect(a).toEqual(b);
  });
});
```

### I — Structural Invariants (modules with bounded outputs)
Verify outputs respect known mathematical bounds: probabilities in [0,1], correlations in [-1,1], dimensions preserved, symmetries, monotonicity.

**Template:**
```js
describe('hardening — invariants', () => {
  it('output values in expected range', () => {
    const r = functionName(data);
    expect(r.field).toBeGreaterThanOrEqual(-1);
    expect(r.field).toBeLessThanOrEqual(1);
  });
});
```

### E — Edge Cases (modules with known extreme results)
Verify textbook-known results for extreme inputs: uniform distribution → specific entropy, perfect separation → NaN coefficients, empty intersection → 0 for similarity.

## Implementation Steps

### Step 1: Add hardening blocks to test files

For each module `.test.js` file, add one or more `describe('hardening — ...')` blocks at the end of the file (before the final closing). Each block follows the established template.

**Priority order:** Batch A first (highest usage), then B through I.

**Rules:**
1. Never modify existing `it()` blocks — only add new `describe()` blocks
2. Each hardening block has 1-3 `it()` blocks with 1-3 assertions each
3. Use `toBeNull()` for invalid inputs, `toBeCloseTo()` for boundary outputs
4. Import functions that aren't already imported
5. No new dependencies or fixtures needed

### Step 2: Migrate existing hardening.test.js content

Move the existing 32 hardening tests from `hardening.test.js` into their respective module `.test.js` files (e.g., `anova.test.js`, `categorical.test.js`, etc.). This consolidates hardening tests with their modules.

Then delete `hardening.test.js` as its contents are now distributed.

### Step 3: Validate

```bash
npm run reference:generate   # verify no regression
npm test -w statlab           # all existing + new hardening tests pass
```

**Expected:** ~4,900 existing + ~150-200 new hardening tests, zero regressions.

## Risk Mitigation

- **Test pollution**: `describe()` block names must be unique within each file. Use `'hardening — invalid inputs'`, `'hardening — degenerate data'`, etc.
- **Import conflicts**: Some hardening tests need functions not currently imported in the test file. Add `import { fn } from './module.js'` at the top.
- **Existing test fragility**: Some modules have very compact tests (single-line `it()` blocks). New hardening blocks should follow the existing style (concise, no comments).
- **Performance**: Hardening tests are fast (no heavy computation). No impact on test suite duration.
